# Isolation

`--hermetic` suppresses the supported harness's automatic loading of specified operator and project customizations. It does not make a result reproducible from a prompt alone. Harness versions, built-in instructions, managed settings, the environment, authentication, and the working directory still matter.

`--tools none` is a separate request to restrict tools. Neither flag replaces the filesystem and network boundary supplied by [scode](autonomy-and-sandboxing.md). Both are headless `run`/`check` options; TUI does not accept them, and a plain `--hermetic` or `--tools none` session is refused — the one hermetic session mode is `session --hermetic --experiment-project-settings` (Claude and Z.AI; see [below](#experiment-project-settings)). The one TUI overlap is structural: Claude and Z.AI TUI launches always pass `--safe-mode`, the same customization-off baseline their hermetic runs use ([TUI restrictions](harnesses.md#tui-restrictions)).

## Supported mechanisms

| --- | --- | --- |
| Claude Code, Z.AI | `--safe-mode` suppresses user/project instructions, skills, plugins, hooks, custom agents, commands, and operator MCP configuration. | Empty built-in tool list. |
| Codex | Private HOME/CODEX_HOME; project document limit zero; user config and execpolicy rules ignored; customization features disabled. Provider overrides use their generated config instead. | Disables shell, execution, image, browser, computer-use, multi-agent, discovery, and web features. **Keeps `update_plan` and `apply_patch`.** Accepted only at read-only autonomy. |
| Antigravity | Private HOME and XDG state, plus rejection of project instruction paths. Requires explicit clean `--cwd` and read-only scode. | Private deny settings and plan mode; rejects native tool attempts after parsing the stream. Requires read-only scode. Tool schemas can remain visible. |
| OpenCode | Private HOME/config/cache/state, real login data retained; discovery and customization channels disabled; login-carried remote configuration refused. | Hermetic runs only. Deny-all permission configuration; plain operator config could override it. |
| Droid | Refused. Instruction, skill, hook, and MCP channels remain. | `--only-tools ToolSearch`; executable tools are excluded. |
| Kimi Code | Private HOME/KIMI_CODE_HOME with filtered config, empty skill directory, and explicit agent profile; rejects project instruction and configuration paths. Sets `KIMI_CODE_NO_AUTO_UPDATE=1` to disable binary updates and `KIMI_CODE_REPEAT_BREAKER=false` so kimi appends no repeated-call reminder to tool results. | Private agent profile with `tools: []`; experiment runs allow only the explicit MCP namespace. |
| Pi | Refused. Global SYSTEM.md and APPEND_SYSTEM.md discovery remains. | `--no-tools`, with autonomy's explicit allowlist suppressed. |
| Goose | Refused. Context files and configured system prompts remain. | `--no-profile`, removing tool-bearing extensions. |
| Aider | Refused. Its config, env, and model-settings discovery can inject content despite pinned files. | Refused. No supported empty tool-set mapping. |

| OpenHands | Refused. Project and public skill loading remains. | Refused. |
| Copilot | Refused. The required paired canary cannot demonstrate isolation under the standing hardening flags. | Refused. Empty allowlist spellings do not remove tools. |
| Gemini CLI, Cline | Refused. Workspace instruction channels remain. | Refused. No verified complete removal mechanism. |
| Qwen | Refused. Every normal run already uses safe mode, so the paired control cannot leak. | Refused. Safe mode ignores the core-tool allowlist; exclusions can miss new tools. |

These are implemented contracts, not a claim that every currently installed upstream release has passed a live check. See [versions and dated evidence](harnesses.md).

Codex's remaining `apply_patch` can write wherever scode permits writes, including writable harness state and scratch storage. Read-only autonomy protects the project, not every path. Unknown upstream feature names may only warn, so a newer Codex can invalidate a feature-based restriction.

Antigravity denies the native `read_file`, `write_file`, `read_url`, `execute_url`, `command`, `unsandboxed`, and `mcp` action classes. A non-text step, permission refusal, nonempty `denied_actions`, unknown step type, or malformed stream fails an ordinary tools-none run. This detects attempted actions; it does not remove their schemas. The MCP action is denied at its native gateway.

## Directory and login requirements

Antigravity hermetic runs require a dedicated clean directory supplied with `--cwd`. Codemux rejects `GEMINI.md`, `AGENTS.md`, and `.agents`, including empty directories and dangling links, in that directory and ancestors through the project root. Executable project configuration checks still apply.

Codex rejects project `.agents/skills` and `.codex/skills`. Its private home is created inside the real CODEX_HOME, where scode can expose harness state. HOME changes only inside the sandbox command; scode still derives its protections from the real operator home.

OpenCode retains its real data directory for login. Before a hermetic launch, codemux rejects well-known auth entries and active account organizations that can fetch remote configuration. Unreadable, oversized, malformed, linked, nonregular, or changed-while-read stores fail closed. The hermetic prefix also removes `OPENCODE_AUTH_CONTENT`. Administrator-managed settings remain. The private state directory receives one copy: the operator's `model.json` (the model preference OpenCode reads when neither `--model` nor a config names one), so a hermetic run uses the model a plain run uses instead of the provider's first; the copy is skipped, with a warning, unless the file is a regular, user-owned, small, valid UTF-8 JSON file.

The Gemini CLI exports the first `.env` it finds walking up from the working directory into its own process. Codemux turns that off through the CLI's system settings layer (`advanced.ignoreLocalEnv`), but the CLI loads that file only from a root-owned path: on a user-owned install prefix (a checkout, Homebrew) it skips the file, so codemux names no settings file there and refuses a repository `.env` on that install instead. `.gemini/.env` and `.gemini/settings.json` are refused on every install.

Kimi Code rejects `AGENTS.md`, `agents.md`, `.kimi-code`, `.agents`, and `.mcp.json` from the Git root through the working directory, including empty directories and dangling links. Outside Git, it checks only the working directory. Its private HOME and KIMI_CODE_HOME live under the real brand home's `.codemux-hermetic` directory. The config retains model, login, and runtime settings, removes operator discovery and hooks, and disables automatic session titles. An explicit agent file prevents project agent overrides, and `--skills-dir` selects a private empty directory. `KIMI_CODE_TRUST_WORKSPACE` is omitted. Passing through KIMI_CODE_HOME is refused because hermetic mode owns that variable. The private `credentials` directory is a symlink to the real credentials directory, so atomic token refreshes reach the shared login. Every hermetic Kimi child sets `KIMI_CODE_NO_AUTO_UPDATE=1` and never updates the installed binary, and `KIMI_CODE_REPEAT_BREAKER=false`, which turns off kimi's repeat breaker (kimi 2.4.0 `agent/toolDedupe/toolDedupeService.ts`): without it kimi appends a system-reminder to the third, fifth and eighth identical tool result in a row and stops the turn after twelve, which changes model-bound tool results. Private update state alone does not prevent replacement of the running executable. Plain runs, including non-hermetic check controls, may update it. Record the Kimi version used in the live-gate notes.

The Kimi command redirects HOME after scode starts, so scode derives its policy from the real home and can expose the shared credentials. Identity and bundled-skill environment overrides are omitted too.
The filtered config retains `default_provider` alongside model definitions.
Kimi 2.3.2 accepts that key and uses it when a model has no explicit provider.

Plain aider runs map instruction directories onto `--read` for each directory's `AGENTS.md` and `CLAUDE.md`, passing only files that exist: aider exits 1 at argv parse when a `--read` file is missing, so an unconditional pair would kill a launch whose directory holds only one of the two names.

[Authentication](authentication.md) explains credential linking, mirrors, rotation, and recovery.

## Verification

`codemux check --hermetic -a <agent>` spends model quota. It plants an instruction canary and requires a clean `OK` reply, then runs a control that must reveal the planted code word. A clean control is inconclusive and fails. A model's tool inventory claim is not a capability test.
Kimi's marker scan includes both stdout and stderr on every run, including
reasoning printed to stderr. A final `OK` does not hide a marker in reasoning.
Codex and Kimi experiments refuse both `--sandbox-no-net` and
`--sandbox-trust untrusted` before launch because their relay needs loopback.

For most harnesses, adding `--tools none` keeps the same tool selection in both runs. OpenCode's combined check is refused: its non-hermetic control cannot legally use tools-none. Check OpenCode hermetic isolation alone; its tool restriction has separate capability evidence.

Antigravity uses paired instruction/MCP and command-denial probes in scratch operator homes. The tools probe requires the first and only command attempt to be denied with no command output; the control must execute a native command and quote its actual output. Combining flags runs both pairs. Probe scratch homes, native logs, and working directories are removed on known exit paths.

Kimi Code plants the instruction code word in a scratch brand home's `AGENTS.md` under the real brand home's `.codemux-canary` directory, where scode can expose it. Its working directory stays clean because hermetic runs refuse project instruction files. Credentials are symlinked to the real directory. The hermetic probe must answer exactly `OK`. The control runs without `--hermetic`, carries the planted brand home on the request itself, and passes KIMI_CODE_HOME through; its private MCP configuration writes land inside the scratch home by construction, not through the planted adapter's environment, and the control must reveal the code word. Adding `--tools none` keeps the empty tool profile in both runs. Scratch homes and the working directory are removed when the check ends.

### Experiment MCP exception

Claude, Z.AI (the same Claude Code binary), Codex, and Kimi accept an explicitly supplied experiment MCP server under `--hermetic --tools none --auto read-only`. Claude/Z.AI require Claude Code 2.1.280 or later. On Claude/Z.AI, safe mode stays enabled, the built-in tool list stays empty, and the explicit server uses the SDK control protocol. This is an intentional exception to suppression of operator MCP configuration.

The experiment server runs **outside scode**, with the run directory as cwd and only named environment variables. Its cwd is not containment. The command must pass the executable trust check and sit outside the run directory. The relay and its server are minted at start, so `--print-sandbox` is refused together with `--experiment-mcp`: the argv cannot be shown without starting it. The host permits requests only for that server and checks inventory and returned content. Persistent raw recordings may contain sensitive data.

Codex requires CLI 0.165.0 or later and `accept_harness_prefix: ["codex-wall-time"]` in the spec. A per-run authenticated loopback HTTP relay connects Codex to the stdio server; `--sandbox-no-net` is refused. Nonempty system MCP configuration is refused because its tables merge into the private home. Windows experiments are refused until the system config location can be verified. Codemux reads the private rollout before cleanup, records the exact model-bound items, and compares them after removing only the accepted `Wall time: ... seconds\nOutput:` header. Built-in tool calls, missing evidence, results carrying `structuredContent` or `_meta`, and truncated output fail the run. Codex spills are not accepted. Codex supports experiment `run` only; paired `check` is refused before a model request.

Kimi requires Code 2.3.2 or later. A private `mcp.json` names only the authenticated loopback relay, and `--sandbox-no-net` is refused. The explicit agent profile allows only the experiment MCP namespace while excluding all built-in tools. The wire log must confirm the exact tool inventory, native calls, per-step usage, and unchanged model-bound results before cleanup. Top-level `structuredContent`, `_meta`, unsupported content blocks, missing evidence, changed output, truncation, and spills fail the run. The paired check keeps the same spec and tool policy in both probes. Its non-hermetic control uses the planted scratch brand home, including the home instruction canary, and a relay-only MCP configuration. Every other adapter still refuses. See [experiment MCP](experiment-mcp.md) for the specification and recording contract.

### Experiment project settings

`--experiment-project-settings` runs a hermetic harness with the repository's own settings in place of the operator's. Claude and Z.AI run with `--setting-sources project,local` in place of `--safe-mode`, inside a **private Claude config directory** created for the run; OpenCode runs inside its usual hermetic private home with `OPENCODE_DISABLE_PROJECT_CONFIG` unset and `--pure` dropped, so the repository's own rules and plugins apply without the operator's user-level customizations. Every other run suppresses repository settings, so they never reach it. The flag requires `--hermetic` and scode. Claude and Z.AI require `--auto low`, because medium grants every shell command and high bypasses the rules; OpenCode also accepts `--auto high` (see below). A passed-through `CLAUDE_CONFIG_DIR` or `CLAUDE_CODE_PROJECT_DIR_NAME` (Claude, Z.AI) or `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT`, `OPENCODE_PERMISSION`, or `OPENCODE_AUTH_CONTENT` (OpenCode) is refused: the run supplies its own configuration. Claude and Z.AI also pass `--disable-slash-commands`, which the binary documents as disabling all skills, user and project alike.

The private directory exists because dropping the user setting source alone is not enough (live check 2026-10-30 10:59, zai, `--hermetic --experiment-project-settings --auto low`): Claude Code ignored the fixture's allow rules with "this workspace has not been trusted … set projects["\<cwd\>"].hasTrustDialogAccepted: true", and the model quoted the operator's user-level CLAUDE.md.

The directory is created per run under `~/.claude/.codemux-hermetic/` and holds only a generated `.claude.json` — onboarding marked complete and the run's working directory marked trusted, so the fixture's rules apply — plus, on a Claude run without a provider override, an access-token-only copy of the credential mirror that is removed with the directory when the run ends ([authentication](authentication.md)). Z.AI and provider-override runs authenticate through their gateway token and carry no operator login. The private directory removes what the config directory would supply: the operator's user memory, user settings, user skills, user hooks, plugins, and per-project state. The operator's `~/.claude.json` and `~/.claude/settings.json` are never read for content beyond the credential mirror and never written.

**Operator harness state unreachable.** Redirecting the config directory does not by itself stop the sandboxed child from touching the real one: scode's default profile keeps `~/.claude` writable as harness state, so on macOS a project-settings run could read or write the operator's transcripts under `~/.claude/projects`, `~/.claude/history.jsonl`, `~/.claude.json`, and every other run's and session's directory under `~/.claude/.codemux-hermetic/`. Under the flag, `run` and `session` therefore pass scode `--block` over the real config root (the effective `CLAUDE_CONFIG_DIR` default, `~/.claude`) and `--block ~/.claude.json`, then `--allow` for the launch's own private directory. A CLI block wins over scode's automatic and config-file harness-state allows, and a child allow re-opens exactly that directory (scode emits the block first, the child allow after, and re-asserts both in its final guards), so the child can write its own transcript and nothing else of the operator's. This was chosen over `--strict`: strict's own detected-harness grant would re-allow `~/.claude` (the same block is needed anyway), and the `untrusted` preset couples in `--ro`, `--no-net`, and `--scrub-env`, which a low-autonomy experiment run needs unset. What remains reachable is what the run needs: the working directory and its project settings, the private config directory, system paths, and whatever scode's default profile allows outside the blocked trees. An operator can add blocks of their own with the repeatable `--sandbox-block <path>` (absolute paths only) on `run` and `session`; that flag is an extra, not the project-settings fix. A block that names the launch's own private directory, one of its ancestors, or any path inside it is refused before the spawn (exit 64, naming both paths): scode emits the child allow after the block, so exactly the blocked tree would be reachable again — and a block inside the allowed directory would be dropped by scode's own recursive allow, so a caller block beneath a launcher-allowed state directory cannot be honored either.

The config directory is not the only road to the operator's CLAUDE.md (live check 2026-10-30 13:00, same flags: a fixture under the home still received it; the same fixture under a scratch root outside the home did not). With the project or local setting source on — which this flag always passes — Claude Code walks every ancestor of the working directory and loads `<ancestor>/CLAUDE.md`, `<ancestor>/CLAUDE.local.md`, `<ancestor>/.claude/CLAUDE.md`, and `<ancestor>/.claude/rules/*.md` as project memory. That walk is the project memory channel itself, so neither the private config directory nor `--setting-sources` limits which ancestors it reads, and at the home directory `~/.claude/CLAUDE.md` is such an ancestor file. Codemux therefore refuses the run before launch (a usage error naming the nearest offending path) when any directory above the working directory carries one of those names — a file, a directory, or a link, including a dangling one. The working directory itself is the fixture's own and may carry them. The home directory normally carries `~/.claude/CLAUDE.md`, so in practice a fixture under the home is refused; place fixtures outside it.

What still loads, by design: `CLAUDE.md` files in the working directory itself, `.claude/settings.json`, and `.claude/settings.local.json` — the point of the flag. Hooks in the project's own `.claude/settings.json`, including PreToolUse hooks, do load and fire under this flag, which experiments may rely on. Project skills do not load: Claude and Z.AI run with `--disable-slash-commands`, which disables all skills, user and project alike. The git identity in Claude's own context snapshot comes from the repository's git configuration, so a fixture should set a local `user.name` and `user.email`. Project settings can run hooks and set environment variables, so use it only on a repository you built, such as a disposable fixture.

On OpenCode, the private home, the real login data directory, the remote-config refusal, and the other `OPENCODE_DISABLE_*` assignments are unchanged. What differs from a plain hermetic run: `OPENCODE_DISABLE_PROJECT_CONFIG` is not set and `--pure` is not passed, so the working directory's own `opencode.json`/`opencode.jsonc`, `.opencode/` (plugins, agents, commands), and the project instruction files load, and the project's plugins run. `--auto low` maps to `--agent build` with no `--auto`; `--auto high` maps to `--agent build --auto`. What a level does to a tool call is the build agent's permission defaults plus the project's own rules, and the defaults allow every unlisted call (`"*": "allow"`) with asks only for a doom loop, an external directory, and an `.env` read — so at low an unlisted bash command or edit is allowed, not asked. A headless run answers every ask with reject (low) and `--auto` approves every ask (high), so a rule written as `ask` rejects at low and passes at high; a fixture that wants unlisted commands rejected writes them as ask rules, e.g. `"bash": {"*": "ask", "touch allowed.txt": "allow"}`. A `deny` rule fails the call before the question is ever emitted, so deny rules bind at both levels.

On OpenCode the operator harness state is not blocked. The real data directory that hermetic runs keep (`XDG_DATA_HOME` unchanged) holds both `auth.json` and the run's own storage — the native session database and run storage live there — so blocking it would deny the run its own writes, and a file-level allow could reopen only `auth.json`, not the run's own tree. A private data directory would mean copying `auth.json` (a refresh-token-shaped credential codemux refuses to copy) and desynchronizing token refresh. The private home, config, cache, and state redirections carry the isolation instead; the data directory stays reachable exactly as in a plain hermetic OpenCode run.

OpenCode rule expressions. `{"permission": {"bash": {"rm *": "deny"}}}` in `opencode.json` denies a shell command whose parsed text the pattern matches: the shell tool parses the command, builds one pattern per parsed command (a redirected command's whole statement text), and denies the whole call when any pattern hits a deny rule. `*` matches any run of characters and `?` exactly one, matching is anchored, and the last matching rule wins with `ask` the default. `edit` patterns are worktree-relative paths, so a project can protect its own rule file from the edit and write tools with `{"permission": {"edit": {"opencode.json": "deny", ".opencode/**": "deny"}}}`. OpenCode has no built-in protection of those files — the bash tool can still write them.

A project plugin at `.opencode/plugin/<name>.ts` exporting `tool.execute.before` and `tool.execute.after` is the PreToolUse/PostToolUse equivalent and fires on every tool call. `tests/fixtures/opencode-project-settings/` holds a tested fixture plugin that appends one JSON line per hook to a file beside itself, plus the rule file above, for a live check. Two side effects on the fixture when `.opencode/` exists: OpenCode writes `.opencode/.gitignore` and runs a background `npm install @opencode-ai/plugin` into `.opencode/`, which needs the network. Under `--sandbox-no-net` that install fails with a logged warning and the run proceeds.

Codemux refuses an OpenCode project-settings run when any directory strictly above the working directory, up to and including the filesystem root, carries `opencode.json`, `opencode.jsonc`, `.opencode`, `AGENTS.md`, `CLAUDE.md`, or `CONTEXT.md` — any entry of that name, including a dangling link. Both of OpenCode's project walks stop at the worktree root, but a working directory without version control gets worktree "/", so the walks can reach the filesystem root; the refusal covers both cases on its own, so no git-root requirement is added. The executable-config refusal for OpenCode skips the working directory itself under this flag. A home directory usually carries an `AGENTS.md` or `CLAUDE.md`, so in practice a fixture under the home is refused; place fixtures outside it. The working directory itself may carry every name. A passed-through `OPENCODE_BIN_PATH` selects the binary the OpenCode launcher execs, so it must name one trusted absolute executable (owned by the user or root, not group- or world-writable, outside the working directory); anything else refuses the run, the launch pins that binary's identity beside the command's own for the pre-spawn re-stat, and the run and interactive version gates read the redirect from the same adapter-built environment the launch uses, so the binary the gate probes is the binary that runs.

Cursor refuses the flag, because its user-level channels cannot be kept out while preserving the login. The login file `~/.cursor/auth.json` holds an access and a refresh token, so a private home would mean copying a refresh token. `CURSOR_CONFIG_DIR` moves only `cli-config.json`; user-level `mcp.json`, `rules`, `commands`, and `plans` are read from the home directory; and the prompt carries account `user_rules` and `cloud_instructions` that no CLI flag disables — the only disable flags are auto-update, codebase-ref, indexing, and `--disable-project-configs`. For the record, the equivalents exist: a project rule file `.cursor/cli.json` with `{"permissions": {"allow": [], "deny": ["Shell(rm)"]}}`, honored unless `--disable-project-configs`, and hooks in `.cursor/hooks.json` (version 1): beforeShellExecution, afterShellExecution, beforeMCPExecution, afterMCPExecution, beforeReadFile, afterFileEdit (no pre-edit hook), beforeSubmitPrompt, afterAgentResponse. No built-in protection of those files was found, and codemux has no authenticated Cursor completion in its contract, so Cursor's headless approval behavior is unverified.

A persistent session takes the same isolation with a different lifetime (see [sessions](sessions.md#hermetic-project-settings-sessions)): `codemux session --hermetic --experiment-project-settings` (the only hermetic session mode — a plain `--hermetic` session is refused) keys the private directory to the native session id as `session-<uuid>` instead of a per-run directory, reuses it on every `--resume`, and removes it only on `--final` or the two-day dead-owner sweep, because the session's transcript and trust record live inside it. The flag also accepts `--auto high` for sessions: the session high is codemux's own grant list, never the bypass flag, so the repository's deny rules still bind.

## Residual inputs and enforcement

- Tools that remain can read reachable working-directory and harness-state files. Hermetic disables automatic customization loading, not arbitrary file access.
- The sanitized environment and explicitly passed variables remain inputs. Hermetic does not create a fixed environment.
- Administrator-managed Claude, Codex, and OpenCode settings can still apply, including managed hooks.
- Vendor system prompts and bundled skills remain and can change with the harness version.
- Safe modes can remove the operator's own hooks and deny rules. Scode supplies filesystem/network restrictions; native harness policies still decide tool exposure and approvals.
- Same-user concurrent processes can modify readable enforcement files or the harness binary. Each spawn re-stats every trust-checked executable it is about to exec and refuses a change to its dev/ino/mode/size/mtimeNs/ctimeNs, so a swapped or in-place-rewritten binary runs only if the change lands in the short window between that re-stat and the exec (ctime cannot be set from user space, so an in-place rewrite always moves the recorded identity). Scode is not isolation between mutually hostile processes owned by the same user.
- Login and server-side account state can affect behavior. Network responses are not pinned.
- Cleanup is not guaranteed after SIGKILL or a host crash.

## What persists

| State | Lifetime and behavior |
| --- | --- |
| Codex hermetic HOME and one-shot provider home | Removed after the run. Stale one-shot directories are eligible only after two days based on the newest tree modification and a dead owner; live owners are retained. |
| OpenCode hermetic home and per-run provider files; Kimi hermetic home and tool profile; Droid/Pi provider files | Removed by their run cleanup. Interrupted runs can leave files for later cleanup. Kimi stale homes use the same dead-owner and two-day age checks as Codex, and the OpenCode hermetic sweep ages a home by the newest modification anywhere in its tree, so an orphaned child still writing under redirected XDG directories is not deleted mid-run. |
| Antigravity private home and file-token/Keychain copies | Removed on known exits; a failed removal is retried by later cleanup calls, the process-exit backstop included. Recovery considers validated, marked, user-owned homes with dead owners; see authentication. |
| Codex real auth.json | Linked into subscription hermetic homes; in-place refreshes persist in the real login. Provider-key runs do not link it. |
| Claude access-token mirror and credential backups | Persistent shared credential state; backups are not temporary run data. |
| Claude/Z.AI project-settings config directory | Per-run directory removed after the run, the per-run access-token copy with it; a session's `session-<uuid>` directory persists for the next `--resume` until `--final` or the two-day dead-owner sweep. |
| Antigravity plain-run settings, conversations, and project state | Existing entries are individually linked from the operator's state. OAuth and probe-root entries are excluded. Medium headless runs use a private settings copy with the command grant instead of the settings link. Hermetic/tools-none runs use private state. |
| Other harness-owned state | May persist according to that harness. A one-shot codemux result does not promise zero disk writes or no native history for every adapter. |
| Calls ledger | Persistent per-call metadata in codemux's state directory, unless explicitly disabled. |
| Experiment recordings | Persistent raw protocol/byte recordings; cleanup of the run does not remove them. Written only inside a real directory owned by the current user, tightened to 0700 at creation; a linked or foreign-owned recording directory is refused. |
| Session registry, native transcripts, session provider homes | Deliberately persistent and resumable. The one hermetic session mode is the project-settings session (Claude/Z.AI; see above), whose private config directory persists for the next `--resume` until `--final` or the two-day dead-owner sweep. |

Claude/Z.AI use `--no-session-persistence`; Codex uses `--ephemeral` for ordinary one-shot runs. Codex and Kimi experiment runs retain their private native logs until delivery checks finish, then remove the private home. Those flags do not erase credential mirrors, shared state, the calls ledger, or experiment recordings.
